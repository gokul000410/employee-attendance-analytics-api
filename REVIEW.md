# REVIEW.md

List of defects identified in the starter `app/main.py` (helpers, endpoints, database configuration, and data models):

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33–37) | Timezone mismatch and incorrect grace period evaluation. `punch_in` in UTC was modified with IST shift hours using `replace(hour=h, minute=m)`, mixing UTC and IST. Furthermore, `int((punch_in - start).total_seconds() / 60) > 10` evaluates 10.5 minutes (09:40:30) as 10, failing to flag 09:40:01–09:40:59 as late (R2). Also did not truncate timestamps to whole seconds (R1). | Punching in at 09:40:30 on a 09:30 shift returned 0 late minutes instead of 10. | Normalized `punch_in` to IST, truncated to whole seconds, created an IST `shift_start` datetime, and checked `diff_sec > 600` before taking `diff_sec // 60`. |
| 2 | `compute_work_hours` (lines 40–41) | Uses Python's built-in `round()`, which applies banker's rounding (round half to even) rather than round half-up required by R4 and R8. Floating-point division also suffers from IEEE-754 precision inaccuracies. | A duration resulting in 2.125 hours rounds to 2.12 instead of 2.13. | Converted exact integer elapsed seconds to `Decimal` and quantized using `ROUND_HALF_UP` with `Decimal("0.01")`. |
| 3 | `compute_overtime` (lines 44–47) | Ignores overnight shifts where `shift_end <= shift_start` (causing `shift_end` to be evaluated on the shift start date instead of the next day) and awards overtime for < 30 minutes. R3 states overtime only counts when >= 30 minutes, otherwise 0. | Punching out 10 minutes after shift end returned 10 overtime minutes instead of 0. On overnight shifts (22:00–06:00), punching out at 06:40 gave a negative or erroneous calculation. | Added overnight shift detection to advance `shift_end` to `date + 1 day`, and enforced `if diff_sec >= 1800` (30 mins), otherwise return 0. |
| 4 | `create_employee` (lines 78–85) | Check-then-insert race condition (`find_one` followed by `insert_one`), no database unique index created on `emp_code`, does not validate that `shift_start != shift_end`, stores naive `datetime.now()` for `created_at` rather than UTC BSON date, and fails OpenAPI schema because `created_at` is returned as a datetime object instead of epoch milliseconds. | Concurrent requests with the same `emp_code` result in duplicate records; setting `shift_start="09:30"` and `shift_end="09:30"` succeeds with 201 instead of 422; client receives string datetime instead of integer epoch ms. | Added unique index on `emp_code`, validated `shift_start != shift_end` (raising 422), stored UTC datetime, caught `DuplicateKeyError` to return 409, and returned `created_at` as epoch milliseconds. |
| 5 | `list_employees` (lines 89–96) | Off-by-one pagination bug `skip = page * page_size`, which skips the first 20 records on page 1. `total` was computed via `db.employees.count_documents({})`, counting the whole collection and ignoring the department filter. Furthermore, records were not sorted by `emp_code` ascending, and `created_at` was not converted to epoch milliseconds. | Calling `GET /employees?page=1` returned items 21–40; `GET /employees?department=Sales` returned `total=6` instead of `2`. | Changed skip to `(page - 1) * page_size`, passed the filter query `q` to `count_documents(q)`, added `.sort([("emp_code", 1)])`, and converted `created_at` to epoch milliseconds. |
| 6 | `punch_in` (lines 100–121) | Multiple defects: (a) If employee is not found, `emp["shift_start"]` raises `TypeError` (500 instead of 404); (b) Date computation `ts.date().isoformat()` uses local system time instead of IST calendar date (R1); (c) Ignores overnight shift date determination (punch-in before shift_end belongs to previous day); (d) Unprotected check-then-insert race condition; (e) Unvalidated status (accepts invalid values); (f) Injects prohibited `id` string and unformatted datetimes. | Calling punch-in for an unknown employee yields 500; concurrent punch-ins create duplicates or raise 500; overnight punch-ins at 00:30 IST get assigned the wrong date. | Checked employee existence (404), converted epoch ms to UTC instant, determined IST date with overnight shift support per R1, enforced unique index on `(emp_code, date)` and caught `DuplicateKeyError` (409), and formatted response to `AttendanceRecord` schema. |
| 7 | `list_attendance` (lines 125–150) | Critical memory and performance defect: fetches the entire collection into Python memory using `list(db.attendance_logs.find(q))` and sorts in Python, causing out-of-memory errors on 100,000 records. Missing secondary sort by `emp_code` ascending. Missing validation that `date_from <= date_to` (returns 200 with empty list instead of 422). Added unwanted `id` field and leaked datetime objects instead of epoch milliseconds. Missing default fallback for legacy records missing `half_day` or `history`. | Calling `GET /attendance` on 100,000 records exhausts RAM or hangs; calling with `date_from=2026-07-20&date_to=2026-07-10` returns 200 instead of 422. | Performed indexing on `("date", -1), ("emp_code", 1)` and executed `.sort(...).skip(...).limit(...)` directly in MongoDB; validated `date_from <= date_to` (422); formatted documents to match schema. |
| 8 | `health` endpoint (lines 72–74) | Returns `{"status": "ok"}` unconditionally without checking if MongoDB is accessible. Contract states it must return 200 only if MongoDB answers a ping, otherwise 503. | Shutting down MongoDB still causes `/health` to return 200. | Added `client.admin.command("ping")` inside a try-catch, returning 503 `Service Unavailable` on connection failure. |
| 9 | Database connection & indexes (lines 18–23) | Client was initialized with naive datetimes (`tz_aware` omitted), which causes naive/aware datetime comparison errors. No indexes were created at application startup. | Starting app against unindexed database resulted in COLLSCAN and race conditions under concurrent requests. | Configured `MongoClient(..., tz_aware=True)`, and added FastAPI `lifespan` hook creating all unique and query indexes idempotently. |
| 10 | Input models & validation (lines 53–67) | `EmployeeIn` and `PunchInIn` models lacked field constraints, regex validations (e.g. `^EMP\d{4,6}$`, email regex), and instant range checks (`EpochMillis` bounds between 100000000000 and 4102444800000). Seconds-looking timestamps were accepted. | Sending `punched_at = 1783312500` was accepted instead of returning 422. | Implemented strict Pydantic models with field constraints matching OpenAPI 3.0 schemas. |

### Examined and determined NOT to be defects
1. **Fixed offset for IST (`timezone(timedelta(hours=5, minutes=30))`):** Indian Standard Time does not observe Daylight Saving Time, so using a fixed offset is accurate and avoids timezone database lookup overhead.
2. **Calendar dates stored as plain ISO strings (`"YYYY-MM-DD"`):** Storing calendar dates as strings is intentional per `DATA_MODEL.md`. A calendar date is not an instant; storing it as a string avoids unwanted timezone shifts and enables direct lexicographical BSON range comparisons (`$gte`, `$lte`).
